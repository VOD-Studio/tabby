# tabby：macOS 支持实施方案

- 日期：2026-11-11
- 状态：代码完成（2026-11-11），等待真机验证。§11 各项下是实施记录；所有 macOS 分支都只在 Linux 上经 `Os::Macos` 与 `Recorder` 测试过，macOS 上的编译与测试靠 CI 的 `macos-15`，真机上都**没有验证**。
- 前置：主方案 `2026-11-05-tabby-tui.md`、托管内核方案 `2026-11-06-managed-core.md`。本方案取代后者 §1 的非目标“不做 macOS / Windows 的授权和自启”中 macOS 的部分；Windows 仍不在范围内。

## 1. 目标与范围

tabby 作为客户端（连接已在运行的 mihomo）用到的 ratatui、crossterm、reqwest、rustls 都跨平台，在 macOS 上本来就能编译运行。不能用的是托管内核：下载、进程托管、登录启动、系统代理、TUN 授权都只按 Linux 写。本方案让 macOS（Apple Silicon 与 Intel，最低 macOS 12）上的功能与 Linux 对齐，并正式发布。

**目标**

- 内核：从 MetaCubeX/mihomo 的 release 下载 darwin 版本；Intel 机型按 CPU 选 v1/v2/v3，Rosetta 下运行的 x86_64 tabby 选 arm64 内核。
- 后台常驻：有 GUI 会话时由 launchd 托管（`gui/<uid>` 域），等价于 systemd 用户单元；没有时（只有 SSH）用现有的后备进程组。
- 登录启动：`~/Library/LaunchAgents/<label>.plist`。
- 系统代理：`networksetup`，对每个启用的网络服务设置并在关闭时恢复。
- TUN：setuid root 内核，用管理员对话框（`osascript … with administrator privileges`）或终端里的 `sudo` 授权。
- 发布：Release 归档（aarch64 / x86_64-apple-darwin，带或不带 mihomo）和 Homebrew tap 公式。

**非目标**

- 不做 `.app` 包、不签名、不公证：tabby 是终端程序，归档里的二进制由用户自行去掉 quarantine，或经 Homebrew 从源码构建。
- 不做 root 常驻的 LaunchDaemon 或 helper 服务（理由见 §6）。
- 不支持 macOS 11 及更早版本（mihomo 默认构建用的 Go 需要 macOS 12）。

## 2. 总体设计：编译时不分平台，运行时选平台

`src/core/mod.rs` 新增 `enum Os { Linux, Macos }`，`ManagedCore` 带一个 `os` 字段：`open()` 用 `Os::current()`（`cfg!(target_os = "macos")`），测试经 `testing::core_at_os` 指定。

- macOS 的分支（plist 文本、`launchctl` / `networksetup` / `osascript` 的参数与输出解析）在 Linux 上同样编译，同样用 `Recorder` 测试。开发机和主力 CI 都是 Linux，这样大部分 macOS 逻辑不必上真机也能覆盖，也避免 `#[cfg]` 带来的 dead_code 与漏测。
- 新用到的外部程序（`launchctl`、`id`、`ps`、`sysctl`、`networksetup`、`osascript`、`mount`）都经过 `Runner`。
- 只有用到平台专属 std API 的地方才写 `#[cfg]`。

## 3. 目录

`directories` 在 macOS 上把 config、data、state 都放到 `~/Library/Application Support/tabby`（没有 state 目录，日志退回 data 目录），并且不看 `XDG_*`。

- 默认沿用它：`~/Library/Application Support/tabby/{config.toml, themes/, core/, tabby.log}`。
- `XDG_CONFIG_HOME` / `XDG_DATA_HOME` / `XDG_STATE_HOME` 设为非空绝对路径时，改用 `<xdg>/tabby`。一来照顾习惯 `~/.config` 的终端用户，二来 `make test` 的隔离（临时 `XDG_*`）在 macOS 上也成立。
- Linux 行为不变。

## 4. 进程管理

### 4.1 launchd（有 GUI 会话时）

`Mode::Launchd`。检测：`id -u` 取 uid，`launchctl print gui/<uid>` 成功即用 launchd，否则用后备进程组。

plist（`Label` 用 `state.unit`，即带随机后缀的 `tabby-mihomo-*`）：

| 键 | 值 | 对应 systemd |
|---|---|---|
| `ProgramArguments` | `kernel_command()` | `ExecStart=` |
| `RunAtLoad` | true | bootstrap 即启动 |
| `KeepAlive` | `{SuccessfulExit: false}` | `Restart=on-failure` |
| `ThrottleInterval` | 2 | `RestartSec=2` |
| `ExitTimeOut` | 5 | 停止宽限（`STOP_GRACE`） |
| `StandardOutPath` / `StandardErrorPath` | `core.log` | journal |

平时用的 plist 放在 `<data>/core/launchd/<label>.plist`（不在 LaunchAgents 里，所以不随登录启动），相当于 `systemd-run` 的临时单元。

| 操作 | 命令 |
|---|---|
| 启动 | 轮转 `core.log`；`launchctl bootout gui/<uid>/<label>`（失败忽略，清掉已加载但已退出的 job）；`launchctl bootstrap gui/<uid> <plist>` |
| 重启 | `launchctl kickstart -k gui/<uid>/<label>` |
| 停止 | `launchctl bootout gui/<uid>/<label>` |
| 状态 | `launchctl print gui/<uid>/<label>`：找不到 → 未运行；`state = running` → 运行；`spawn scheduled` → 启动中；未运行且 `last exit code` 非 0 → 失败 |
| 日志 | `core.log` 末尾（与后备进程组相同） |

### 4.2 后备进程组

已有实现在 macOS 上可用（`process_group(0)`、`kill`）。缺的是进程身份：没有 `/proc/<pid>/stat`，原来只能用 `kill -0` 判断 pid 是否存在，pid 被复用时会认错。改用 `ps -o lstart= -p <pid>` 取启动时间（解析为 epoch 秒），与记录的值相等才算同一个内核。`Process.start` 的单位因平台而异，只做相等比较。

### 4.3 登录启动

`~/Library/LaunchAgents/<label>.plist`，内容同 §4.1。开启时若内核正由临时 plist 运行，先 `bootout` 再 `bootstrap` LaunchAgents 里的这份；之后 `launch()` 见它存在就 bootstrap 它。关闭时删除文件，正在运行的内核不动（与 Linux 一致）。macOS 13 起写入 LaunchAgents 会弹“已添加后台项目”通知，用户可以在“系统设置 › 通用 › 登录项”里关掉它。

## 5. 系统代理

`Desktop::Macos`，macOS 上不看 `XDG_CURRENT_DESKTOP`。

- 服务：`networksetup -listallnetworkservices`，去掉第一行说明，跳过 `*` 开头（已禁用）的服务。
- 开启：对每个服务先保存 `-getwebproxy`、`-getsecurewebproxy`、`-getsocksfirewallproxy`（各自的 Enabled / Server / Port）和 `-getproxybypassdomains`，再设绕过列表，最后 `-setwebproxy` / `-setsecurewebproxy` / `-setsocksfirewallproxy <svc> 127.0.0.1 <port>`（这三条同时打开代理，放在最后，避免流量走进设了一半的代理）。已经开着再开（端口变了）时沿用第一次保存的状态。
- 关闭：原来开着的写回原来的 server 和 port，原来关着的 `-set…proxystate <svc> off`；绕过列表写回，原来为空时传 `Empty`。
- `system-proxy.toml` 的 `Saved` 增加 `services`（`#[serde(default)]`，Linux 写的文件照旧可读）。

## 6. TUN 授权

macOS 没有文件能力，建立 utun 和改路由都需要 root。选 setuid root：

- 授权：`chown root:wheel <kernel> && chmod 4755 <kernel>`。图形方式用 `osascript` 的 `do shell script … with administrator privileges`，路径经 `on run argv` 传入并用 `quoted form of`，不拼进脚本文本；用户取消（`-128`）不重试；没有 GUI 会话或没有 `osascript` 时改走终端 `sudo /bin/sh -c 'chown root:wheel "$1" && chmod 4755 "$1"' tabby <kernel>`。
- 判断：内核（`canonicalize` 后）属主为 0 且带 setuid 位，用 `MetadataExt` 读取，不调外部程序。
- 替换内核（升级）会丢掉 setuid，现有的“TUN 打开但没有授权就关掉并提示”逻辑直接适用。
- 内核所在卷以 `nosuid` 或 `noowners` 挂载时 setuid 无效，事先提示。macOS 从 `mount` 的输出判断；外置盘默认是 `noowners`。

**为什么不用 LaunchDaemon**：以 root 运行在 system 域，启动、停止、重启每次都要提权，和用户域托管的流程完全不同；还要保证 tabby 升级的内核不会让 root 守护进程执行任意二进制，需要 FlClash helper 那样的哈希校验（托管内核方案 §2 已说明 tabby 不做）。

**代价**：setuid root 的内核本机任何用户都能以 root 身份运行，并给它任意配置，安全性弱于 Linux 的 `cap_net_admin`。授权确认框会写明这一点，TUN 默认关闭，只在用户确认后授权。

## 7. 内核下载

v1.19.33 的 darwin 资产（`gh api repos/MetaCubeX/mihomo/releases/tags/v1.19.33` 核对）：`mihomo-darwin-arm64-<tag>.gz`、`mihomo-darwin-amd64-v{1,2,3}-<tag>.gz`，另有 `-go120/-go122/-go124`（旧 Go，为旧系统）和 `compatible`，这两类不用。

- CPU 档位：`sysctl -n machdep.cpu.features machdep.cpu.leaf7_features machdep.cpu.extfeatures` 的名字映射成 `/proc/cpuinfo` 的写法，复用 `amd64_level`。
- Rosetta：`sysctl -n sysctl.proc_translated` 为 1 时选 arm64。
- Go 链接器给 darwin/arm64 二进制做了 ad-hoc 签名；gzip 解包保留原样，reqwest 下载的文件不带 quarantine，可以直接运行。

## 8. 打包与发布

- `packaging/mihomo.env` 增加 darwin arm64 与 amd64-v1 的 sha256。
- `scripts/dist.sh`：增加 `*-apple-darwin`；`sha256sum` 缺失时用 `shasum -a 256`；tar 用支持 `--sort` 的那个（macOS 上是 `gtar`）；不用 GNU 才有的 `install -D`；`MACOSX_DEPLOYMENT_TARGET=12.0`。
- `release.yml`：`macos-15` 构建 `aarch64-apple-darwin`，`macos-15-intel` 构建 `x86_64-apple-darwin`。
- `ci.yml`：test 与 clippy 加 `macos-15`。
- Homebrew：`packaging/homebrew/tabby-mihomo.rb` 从 tag 的源码归档构建；`scripts/brew.sh`（`make brew`）在 tag 推送后更新 url 与 sha256；发布即把公式复制进 tap 仓库 `homebrew-tabby` 并推送。公式名与 AUR 一样用 `tabby-mihomo`。

## 9. 风险

| 编号 | 风险 | 应对 |
|---|---|---|
| R1 | 内核以 euid root 运行后，`<data>/core/home` 里新建的 `cache.db`、geo 文件归 root；setuid 丢失后普通身份的内核写不了它们 | 真机验证；如确有问题，在 TUN 因失去授权被关掉时处理这些文件或提示 |
| R2 | `launchctl print` 的输出格式没有文档保证 | 只认少数几个键；fixture 按真机输出更新 |
| R3 | `networksetup` 对标准用户（非管理员）可能要求授权 | 失败以提示呈现；真机验证 |
| R4 | macOS 13 起 LaunchAgents 会被“登录项”管理，用户关掉后 bootstrap 失败 | 失败以提示呈现；真机验证 |
| R5 | osascript 在没有 GUI 的会话里的错误码 | 真机核对，归入“改走终端” |
| R6 | setuid root 内核的权限过大 | §6 的确认文案；默认关闭 |

## 10. 测试与验证

- 每个提交：Linux 上 `make check`；推送后 CI 的 `macos-15` 任务通过。
- macOS 分支在 Linux 上经 `Os::Macos` 与 `Recorder` 测试：命令与参数、输出解析、状态判断、恢复路径。
- 真机（Apple Silicon）：临时 `XDG_*`，一次性 mihomo（只有 DIRECT，非默认端口）。事后没有残留的 `tabby-mihomo-*` job 与 plist，系统代理恢复原状；setuid 只在用户同意后对临时内核做。

## 11. 提交计划

每项一个提交，完成即提交。实施记录写在各项下面。

1. `docs: plan macos support`：本文。
2. `feat(config): honor xdg directories on macos`（§3）。
   - `src/os.rs` 的 `Os` 先落在这里（`config::Dirs` 是它的第一个调用方）。`Dirs::resolve(os, project, env)` 是纯函数，测试在 Linux 上给 `Os::Macos` 和伪造的环境变量。没有 state 目录时日志跟着 data 走（包括 data 来自 `XDG_DATA_HOME` 的情况）。
3. `ci: run the gate on macos`（§8），修掉在 macOS 上不成立的测试。
   - 实际顺序在第 5 项之后：后备进程组的测试在 macOS 上原本会走 `kill -0`，把测试进程自己的 pid 认成内核并发 `TERM`。clippy 与 test 都加了 `macos-15`。在 push 之前没有跑过 macOS CI，可能还有只在 macOS 上失败的测试（如 `/var` → `/private/var` 的路径比较）。
4. `feat(core): download the darwin kernel on macos`（§7）。
   - `Target { os, arch, flags, translated }`，`Target::of(os, arch, runner)` 便于测试任意架构。`amd64_level` 改为按 flag 列表判断，Linux 与 macOS 各有一个解析函数；`LZCNT` 映射为 `abm`。只在 x86_64 的 Mac 上调用 `sysctl`。
5. `fix(core): tell the fallback kernel from a reused pid on macos`（§4.2）。
   - `ps -o lstart=` 的输出受 locale 影响，所以不解析，而是取 sha256 的前 8 字节存进 `pid_start`，只做相等比较。`testing::core_at` 固定为 `Os::Linux`；跑真实进程的测试改用 `Os::current()`，并用 `ps` 读取进程组和命令行，不再读 `/proc`。
6. `feat(core): run the kernel under launchd on macos`（§4.1）。
   - 与方案的差别：重启不用 `kickstart -k`，而是重写 plist 后 `bootout` + `bootstrap`，这样换了内核路径也能生效。`bootout` 之后轮询 `print`，等 job 消失再 `bootstrap`，避免“已加载”的错误。`core.log` 先以 0600 新建，launchd 往里追加。`launchctl print` 只读缩进一层的键。
7. `feat(core): start the kernel at login through a launch agent`（§4.3）。
   - `launchd_launch` 在 LaunchAgents 里有 plist 时用那一份，否则用自己目录里的。`NeedsSystemd` 改名为 `NeedsServiceManager`；`activate_setting` 超出 100 行，改用 `Gate::refusal()` 统一给出提示文案。80×24 和 60×20 下设置页的文案都没有截断。
8. `feat(core): set the macos system proxy with networksetup`（§5）。
   - 恢复时，原来关着的代理只执行 `-set…proxystate off`，服务器字段仍然留着内核的地址，与 GNOME 只恢复 mode 的做法一致，避免短暂启用旧代理。
9. `feat(core): authorize tun on macos with a setuid kernel`（§6）。
   - 没有 GUI 会话（`Mode` 不是 `Launchd`）时直接改走终端，不运行 `osascript`。`osascript` 失败时只把 `(-128)` 当作取消，其他错误原样显示。macOS 的 `nosuid_mount` 同步运行 `mount`（在 UI 线程上，耗时以毫秒计）。确认框与 nosuid 提示按 `core.os()` 显示不同文案。R1（root 写入的文件归属）还没有处理，等真机结果。
10. `build(dist): pack macos archives`（§8）。
   - 在 Linux 上重新跑过 `make dist`，归档和 `SHA256SUMS` 都正常。macOS 那部分没有运行过。
11. `ci(release): build macos archives`（§8）。
   - 依赖 GitHub macOS 镜像自带的 `gtar`；没有它时 `dist.sh` 会报错并提示 `brew install gnu-tar`。还没有经过一次真实的 tag 发布。
12. `build(brew): homebrew formula for the tap`（§8）。
   - 与方案的差别：homebrew-core 有 `mihomo`，但没有设为依赖。tabby 会自己下载内核，装了 `brew install mihomo` 时也会通过 `$PATH` 使用它，caveats 里有说明。`make brew` 已对 v0.2.2 跑过两次（第一次写入，第二次校验未变）。tap 仓库 `VOD-Studio/homebrew-tabby` 还需要创建。
13. `docs: record macos decisions`：README、AGENTS.md、本文的实施记录。

**待真机验证**（Apple Silicon）：§10 的清单，以及 R1–R5。
